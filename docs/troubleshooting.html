Chapter 9 Troubleshooting

“lazy-load database is corrupt” / “interrupted promise evaluation”

R memory-maps the package’s .rdb file during library() and doesn’t release the handle on reinstall. If a second R process reinstalls the package while the first one still has it loaded — or the same session reinstalls itself — you’ll see one of:

Error: lazy-load database '.../scminerViewer.rdb' is corrupt
Warning: restarting interrupted promise evaluation
Error in R_decompress1

The crude fix is the recipe most blogs prescribe: quit every R session holding the package, wipe the install dir, reinstall from a fresh session. Three better options:

1. Don’t library() during development — use devtools::load_all()

load_all() reads the package source directly; no .rdb is ever written, so the corruption literally cannot happen.

devtools::load_all("scminerViewer")     # Cmd/Ctrl + Shift + L in RStudio

This is what 90% of R package developers use day-to-day. library() is for end-users.

2. RStudio: tick “Restart R prior to install”

Tools → Project Options… → Build Tools → Restart R prior to install and clean — then Build → Install Package (Cmd/Ctrl + Shift + B) kills the R session before each install. Costs you the session state, but guarantees a clean .rdb.

3. Use the shipped safe-install helper for scripted installs

scminerViewer/inst/scripts/install.R unloads the namespace, GCs to release mmap pages, wipes the install dir, then installs in a fresh callr subprocess — so the parent R never holds a stale handle.

source(system.file("scripts", "install.R", package = "scminerViewer"))
safe_install("scminerViewer")                # auto-detects .libPaths()[1]
safe_install("scminerViewer", lib = "/path/to/lib")

Or from a shell:

Rscript scminerViewer/inst/scripts/install.R scminerViewer

The helper cannot unload the package from other R sessions on the same machine — those have to quit on their own first.

Last resort: manual cleanup

If everything’s stuck:

  1. Quit every R session that has the package loaded — in RStudio use Session → Quit Session / Cmd/Ctrl + Q. (Restarting alone isn’t enough; the OS still has the old .rdb mmap’d until the process exits.)

  2. Wipe the install directory from a shell:

    rm -rf "$HOME/StJude/Research/R_lib/scMINERViewer/scminerViewer"

  3. Reinstall from a fresh R session.

meta.csv not found: data/<sid>/expression_files/<sid>/meta.csv

The bundle resolved its shard_dir to its parent directory but the shards live somewhere else. Either move the shards into the bundle’s parent:

mv data/example/expression_files data/2327/
mv data/example/activity_files   data/2327/

…or tell the app where they are at launch time:

run_app("data/2327/2327.scminer.h5",
        shard_dir = "data/example", port = 8000)

run_browser("data", shard_dir = "data/example", port = 8000)
scminer-viewer run data/2327/2327.scminer.h5 --shard-dir data/example
scminer-viewer browse data --shard-dir data/example

No documentation for 'prepare_study'

The package was installed without man pages. Regenerate via roxygen2:

roxygen2::roxygenise("scminerViewer")    # writes NAMESPACE + man/*.Rd

…then reinstall.

could not find function "%>%"

Older versions of the package used magrittr’s pipe in plot helpers without importing magrittr. The current version uses base R 4.1+ |> throughout, so reinstall to get the fix.

Plotly “No trace type specified … Setting the mode to markers”

These warnings used to come from plotly::plotly_empty() placeholders. The current version uses an explicit empty scatter trace (.empty_plot()) and the warnings should be gone — if they still appear, reinstall.

run_browser shows no studies

Run discover_studies(root) from R (or scminer-viewer list <root> in Python) to see what the browser would find. Each study must:

  • be in its own subfolder named exactly the studyID, and
  • contain a file named <studyID>.scminer.h5 (matching the folder name).

A study folder produced before the multi-study refactor sits flat under the root (<root>/Cell/, <root>/Gene/, etc.); it must be wrapped in <root>/<studyID>/ to be picked up. The build_2327_bundle.R script does this automatically.

A gene I expect is missing from the picker

The picker is populated from the bundle’s genes/symbol group, which is the master gene list (every gene in the study, regardless of which matrices have shards). If a gene is missing here, regenerate the bundle.

If a gene is in the picker but gene_values() returns NULL for a particular relationship, the gene isn’t in that matrix’s index — check study$expression_index / $activity_tf_index / $activity_sig_index (R) or study.expression_index etc. (Python). Activity matrices typically have a smaller index than expression (only TFs / SIGs are computed).

Bundle is huge (>1 GB)

The bundle format (bundleVersion == 1) stores indexes only — no matrix values — so a healthy .scminer.h5 is tens of MB even for studies with hundreds of thousands of cells. A multi-GB bundle is almost always an artifact written by an older non-lazy tool that inlined the expression matrix into HDF5 directly. Rebuild via prepare_study(config_path) (Chapter 3); the lazy writer drops the matrix values onto disk as per-gene gzipped CSVs under expression_files/<studyID>/ and activity_files/<studyID>/.

A specific cluster disappears with sampling on

The per-cluster proportional sampling keeps at least one cell per cluster (max(1L, round(n * pct / 100))) so no cluster vanishes entirely. If you see an empty cluster, the cluster has zero cells in the underlying study — check study$clusters$count (R) / study.clusters['count'] (Python).

Error: attempt to construct sparseMatrix with more than 2^31-1 nonzero entries

R’s Matrix::sparseMatrix() caps dgCMatrix at .Machine$integer.max non-zero entries (~2.15 billion). On a single study this only matters if the actual non-zero count of exprs(expression_eset) exceeds that limit. A 30 k-gene × 650 k-cell matrix at 100 % density has 1.95 × 10¹⁰ entries — far over the cap; the same shape at 5 % density has under 10⁹ and is fine.

Two layers protect against this in the portal benchmark:

  1. scminerViewer is already row-streaming. extract_expression() and extract_activity() no longer cast the source matrix to dgCMatrix. The shard writer (.write_graph_shards) iterates genes one at a time and never materializes a full sparse copy, so it works on dense (dgeMatrix, base matrix) and sparse (dgCMatrix) inputs alike.

  2. portal_studies.R reports actual nnz but no longer pre-emptively skips. It still counts non-zero entries on load (length(m@x) if sparse, sum(m != 0) if dense) and prints a warning if the value exceeds the cap. The run is allowed to proceed because the shard writer streams genes; if .reindex_rows() then fails on a huge activity matrix downstream, the run-loop’s tryCatch tags the row as status = "error-too-large". The bsub task still exits 0 either way so the job-array merge dependency fires.

If you hit this error from your own pipeline (not through portal_studies.R):

  • Confirm exprs(eset) is sparse — class(exprs(e)) should report "dgCMatrix" or "dgeMatrix", not just "matrix". A dense base matrix gets re-allocated when any downstream code casts it.
  • Avoid as.matrix(big_eset) or methods::as(..., "CsparseMatrix") on huge inputs; iterate by row instead.
  • If your data genuinely has > 2³¹ nnz, you need a different storage backend (HDF5Array, BPCells, or your own gene-by-gene shard pipeline). scminerViewer’s bundle format already supports this in spirit — the shard tree is per-gene, no single sparse matrix is ever required at rest.
